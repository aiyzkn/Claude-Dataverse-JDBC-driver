# 性能試験の自動化と性能リグレッション（WBS 3.3.1）

本書は負荷試験（NBomber）と性能リグレッション CI の使い方をまとめる。

## 方針（何を CI で守り、何を実機で測るか）

- **CI（`.github/workflows/ci.yml`）= 正当性の回帰ゲート**。ビルド健全性＋単体テスト（159 件：SQL パーサ・
  型変換・名前解決・進捗・ドライラン・本番ガード・CSV パーサ等のローカルなホットパス/ロジック）を push/PR で検証。
  **実 Dataverse は使わない**（CI に資格情報が無く、Dataverse のサービス保護で throttle 律速＝再現性が無い）。
- **NBomber 負荷試験（`bench/Gateway.LoadTest`）= dev 実機での E2E スループット計測**。稼働中ゲートウェイに
  Flight SQL の SELECT を並列負荷でかけ、RPS/レイテンシを計測。手動または定期実行（CI 外）。
- **書き込み系スループット**（バルク/EM/N:N/削除）の E2E 実測は 2.6.4（100 万行受入）・1.4.2・C-3 の方法論
  （縮小プロキシ→外挿）を用いる。

## NBomber 負荷試験の実行

前提: ゲートウェイ起動済み（`DATAVERSE_*` 環境変数で dev に接続）。

```bash
# 別ターミナルでゲートウェイ起動(ClientSecret 等)
# 負荷試験(既定: SELECT 読み取り、5rps、20秒)
export DOTNET_ROLL_FORWARD=LatestMajor
dotnet run --project bench/Gateway.LoadTest -c Release
```

設定（環境変数）:

| 変数 | 既定 | 説明 |
|---|---|---|
| `LOAD_GW` | `http://localhost:32010` | 接続先ゲートウェイ |
| `LOAD_SQL` | `SELECT TOP 10 accountid, name FROM account` | 負荷対象クエリ |
| `LOAD_RATE` | `5` | 毎秒リクエスト数（Simulation.Inject） |
| `LOAD_DURATION` | `20` | 継続秒数 |

出力: コンソールの NBomber サマリ（ok/fail 件数・RPS・レイテンシ min/mean/max・p50/p75/p95/p99）と、
`reports/` 配下の HTML/CSV/MD レポート（`loadtest_flight_select`）。

### 実測例（dev、スモーク）
`rate=3rps / 10s / SELECT TOP 5 account`: ok=30 / fail=0 / RPS=3 / latency mean≈1.96s・p95≈4.28s。
※レイテンシは dev の Dataverse 往復＋ゲートウェイ処理。RPS は Inject 指定値に追従（飽和時は fail/遅延で顕在化）。

## 性能リグレッションの運用

- **相対比較**: 同一 SQL・同一 `rate/duration` で定期実行し、レイテンシ（mean/p95）と fail 率の推移を比較。
  悪化（p95 の顕著な上昇・fail 発生）が出たら、直近のコード変更（読み取り経路/シリアライズ/バッチング）を疑う。
- **飽和点の把握**: `LOAD_RATE` を上げて fail/レイテンシが跳ねる点を探す（dev はサービス保護で頭打ちになる）。
- 書き込み側は throttle 律速のため、NBomber の read 負荷＋2.6.4/C-3 の書き込み外挿で総合評価する。

## CI（性能リグレッション回帰ゲート）

`.github/workflows/ci.yml`（push/PR on main）:
1. `dotnet test src/Gateway.Tests`（単体 159 件）
2. `dotnet build src/Gateway.Host`（ホスト）
3. `dotnet build bench/Gateway.LoadTest`（負荷試験ハーネスのビルド健全性。実行はしない）

→ ロジック/パーサ/変換のリグレッションを push/PR で早期検知。E2E 性能は上記 NBomber を dev で実行。
